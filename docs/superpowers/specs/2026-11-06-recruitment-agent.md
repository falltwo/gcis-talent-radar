# 招募 Agent 方案研究：以使用者方便優先

查核日期：2026-11-06。依官方公開文件與目前 PR #46 刊登招募模組整理。本文是設計建議，沒有安裝框架或修改產品程式。

## 建議

採用 **單一 Luna 對話主控＋LangGraph 持久化工作流＋Jev／Playwright 瀏覽器工具**。保留現有 FastAPI、Pydantic、職位範本、薪資解析與前端版面。先不引入整套 LangChain，也不建立多個對話 Agent 相互接力。

使用者只面對一位助理：正常說話、隨時補充或修改、看到目前資料與進度；中斷後回到同一個招募任務。只在真正缺少必要資料或最後送審時需要使用者操作。

這是對我們需求的適配判斷，並非市占排名或模型效能實測結論。

## 官方做法與可借用的部分

| 代表 | 官方可查的做法 | 我們應借用的部分 | 適配判斷 |
|---|---|---|---|
| Codex | Harness 維護對話、工具、進度事件與批准；產品保有自己的介面及業務紀錄。[官方說明](https://developers.openai.com/blog/codex-as-a-platform) | 任務持續存在、工具執行後核對結果、進度回報 | 借用工作模式；直接遷移整個 Codex runtime 不是本案必要條件 |
| Claude Code | 蒐集上下文、行動、驗證的迴圈；可恢復 session，工作中可中斷或補充方向。[官方說明](https://code.claude.com/docs/en/how-claude-code-works) | 修改需求不重開任務；已完成工作不重跑 | 學習互動體驗；不要求 HR 使用開發者終端機 |
| OpenAI Agents SDK | Runner 處理 Agent loop 與工具；應用仍管理部署、儲存及批准。[官方說明](https://developers.openai.com/api/docs/guides/agents/sdk) | 明確工具界線、結構化參數、工具結果回饋 | 可行替代方案，但仍須另外設計招募業務狀態 |
| LangGraph | 可混合固定規則與模型步驟；提供持久化、串流及人工介入，且不要求使用 LangChain。[官方說明](https://docs.langchain.com/oss/python/langgraph/overview) | 把等待輸入、重試、人工檢查與接續工作變成明確狀態 | 最貼近目前已發生的斷線、補欄位及重跑問題 |

Codex／Claude Code 是完整產品與執行環境；Agents SDK／LangGraph 是可嵌入我們服務的開發元件，不是同一層級的四個替換品。

## 為什麼選 LangGraph，而不是只改 prompt

LangGraph 的 checkpointer 保存同一 thread 的執行狀態；interrupt 可停下來等待人類輸入，再恢復流程。正式使用要搭配持久化儲存，不能只用記憶體 saver。[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)、[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)。

我們需要保存的不是只有聊天原文，還有：

- `task_id`：這次招募任務；重新整理不自動產生全新任務。
- `jobs`：用穩定 job_id 保存各職位、人數、地點、薪資及內容。
- `pending_question`：正在問哪個職位的哪個欄位、預期資料類型。
- `field_sources`：使用者指定、職業範本、AI建議、薪資行情、人為修改的來源。
- `revision`／`reviewed_revision`：目前資料版本，以及人類實際確認的版本。
- `execution`：外站職缺ID、已核對欄位、最後完成步驟及可能尚未確認的寫入結果。

聊天記憶可以摘要或到期，但仍在處理的業務任務不應因此消失。LangGraph 幫助保存與接續；上述資料結構仍須由我們正確設計。

## 使用者應該看到的流程

> 使用者：在太平區設廠，想招現場技術人員。
>
> 助理：預計招募幾位？
>
> 使用者：5
>
> 助理：收到，現場技術人員5位、太平區。我會先擬定工作內容並填入招募網站；薪資未指定，先標示面議。

系統知道上一題在等人數，所以將「5」當作該欄位的回答並驗證，而不是再次猜整句意圖。若使用者改問薪資行情，回答問題後仍保留原本等待中的招募條件。

若對話裡包含「當地起薪中位數31,500元」，先保存為行情參考，不自動視為企業核定薪資；使用者明確指定採用後才更新薪資欄位。

## 模型與程式如何分工

| 元件 | 建議職責 |
|---|---|
| Luna | 以目前任務與對話理解使用者目的，提出結構化欄位修改、需要追問的欄位及工具選擇；擬定缺漏內容 |
| LangGraph | 決定流程停在哪裡、保存狀態、等待輸入、路由工具及恢復工作 |
| 現有 Python／Pydantic | 核對欄位、人數、薪資、來源、權限與版本，保存正式招募資料；避免模型輸出直接變成寫入 |
| Jev | 在瀏覽器階段選擇頁面操作與異常恢復方式，保留使用者要求的操作模型分工 |
| Playwright | 執行已驗證內容、讀回結果、回報實況；不讓模型任意改寫核定內容 |
| 使用者 | 缺必要資料時補充、需要時接手；填完直接手動修改並確認送審 |

保留規則驗證金額、上下限、幣別、職缺ID與版本；降低「看到請問就一定是查詢」這類關鍵字規則對語意判斷的支配。欄位證據可以來自多輪對話：職稱來源一則、人數來源另一則，加上正在等待的欄位脈絡，不再要求一定在同一段文字裡寫完整單位。

建議工具保持少量且有業務意義：查職缺資訊、更新招募條件、補擬工作內容、填寫職缺、核對結果、送審。普通確認回覆沒有資料變更時，不啟動建表或填表工具。

## 便利性優先的6項要求

1. **補一句就能接續。** 人數可以回答「5」「五位」；只問真正缺的必要欄位。
2. **修改只改差異。** 「全端改3位」不刪前端；改薪資不新增另一個外站職缺。
3. **輸入不中斷。** 工作中仍可補充指令；協調到安全邊界暫停後套用最新版本，避免一邊填舊資料、一邊改新資料。
4. **資料來源看得懂。** 顯示「你指定」「AI建議」「行情參考」，不把市場開價當企業承諾。
5. **可接手、可續作。** 加入暫停、接手、繼續；重新啟動服務後先核對已保存內容，再繼續缺少部分。
6. **最後一次確認。** 不增加填表前的大型確認表單；填完直接讓人改，確認最新版本後才送審。人工修改預設不再交AI重寫。

同頁直接操控需要真正的互動式瀏覽器控制層；現有JPEG元件本身做不到。可借用 Claude Code Chrome 整合「可見操作、遇登入或CAPTCHA由使用者處理」的互動原則，但不是直接移植其產品整合。[Claude Code Chrome 文件](https://code.claude.com/docs/en/chrome)

## 三種方案的取捨

| 方案 | 使用者體驗 | 導入範圍 | 建議 |
|---|---|---|---|
| 繼續在現有規則上補案例 | 單一案例能改善，跨步驟修改與恢復仍需自行處理 | 最少 | 適合作為短期止血，不作長期主方案 |
| LangGraph＋現有模型與工具 | 可明確管理等待欄位、人工修改與續作；保留目前介面 | 中等，可分段導入 | 本案首選 |
| 整體改用 Codex／Claude Agent 平台或更換模型 | 可以取得成熟Agent能力，但登入、瀏覽器、業務狀態與產品整合仍須設計 | 較大 | 未證明有必要前不優先 |

LangChain 在需要統一大量模型、檢索器及第三方整合時可再評估；我們已經有可用的模型呼叫與工具，第一階段不需要為了使用 LangGraph 一起改寫這些介面。

## 建議導入順序與驗收

### 第一段：對話與業務狀態

先包住現有模型呼叫，建立持久化 task/job/pending_question；逐步合併意圖與欄位修改決策。驗收「5」「yes」「全端改3位」「只修改公司名稱」「詢問薪資不修改既有職缺」。

### 第二段：填表接續與差異更新

將現有JeV／Playwright工作變成可追蹤工具。保存外站ID與檢查點；失敗只補缺漏、不盲目重建。薪資以最終欄位讀回值核對，改人數不重建同一職缺。

### 第三段：可接手的同頁瀏覽器

保留現有版面，加入可互動瀏覽器控制、互斥操作權與登入隔離。真人接手時停止Agent寫入；繼續前重新讀回頁面資料。

### 驗收案例

- 助理問幾位，回「5」能接續原職位。
- 兩個職位只改其中一個，不丟另一個與原薪資。
- 「請問可以幫我招募」仍能建立招募任務。
- 普通「yes」不新增批次、不當成送審授權。
- 行情31,500只列參考，未獲明確指定不變成企業薪資。
- 擬稿或瀏覽器失敗後保留使用者條件，提供可續作的狀態。
- 服務重啟後能找回任務；恢復前核對外站結果，不承諾恢復同一個Chrome程序。
- 人工修改後依最新版本送審，AI不自動覆蓋。
- 送審回應遺失時先核對外站狀態，不直接再送一次。

## 必須保留的邊界

LangGraph 的 retry 可能從節點開頭重新執行，checkpoint 不等於外部網站寫入恰好一次。建立職缺、儲存及送審必須設計去重與結果查核；若外站不支援 idempotency key，更不能把缺少回應當成沒有送出。[官方 Fault tolerance 說明](https://docs.langchain.com/oss/python/langgraph/fault-tolerance)

框架也不會自動解決職稱理解、欄位證據、瀏覽器接手或正式104／1111登入與刊登權限。應先以小型工作流通過上述案例，再逐段遷移，保留現有可用驗證與人工送審限制。
