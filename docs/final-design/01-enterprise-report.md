# 設計一：完整企業多區比較報告

狀態：保留設計 v1；核心本機MVP已實作。共用版本、名詞與狀態見 [總規格](README.md)，實際範圍見 [交接](../REPORT_IMPLEMENTATION.md)。

## 1. 使用者任務與頁面流程

目標使用者是正在安排擴產、招募或遷廠評估的臺中製造業負責人／人資。完成條件是能比較、理解限制、提出下一步調查並帶走報告。

```text
/compare
  → 選擇2–3區、製造中類與職類
  → 確認觀測期間及招募計畫
  → resolve解析並固定來源release
  → 確認期別，提交resolution_token建立不可變報告
/reports/{report_id}
  → 摘要 → 並排比較 → 證據 → 企業計畫
  → 對本報告追問 → 列印／JSON
```

正式流程不經 `/legacy`。沿用既有比較 CSS／JS 的合適部分，讓它從新版導覽進入。

## 2. 輸入與輸出的對應

| 輸入 | MVP規則 | 改變的輸出 |
|---|---|---|
| 行政區 | 臺中2–3區、不重複；前端保留使用者順序 | 比較欄、當地職缺、公司事件與可用工廠資料 |
| 製造業中類 | 單選；碼與版本由catalog提供 | GCIS事件與可精確對應的工廠列 |
| 職類檢索 | MVP採keyword，1–60字；保留正規化與原輸入 | 同條件的公開職缺與相應摘要 |
| 職缺檢索profile | MVP固定既有製造相關職務規則；伺服器記版本 | 說明查了哪些職務文字，而非雇主正式行業 |
| 觀測模式 | `LATEST_AVAILABLE`或`FIXED_MONTH` | 各資料組可用期別與歷史資料限制 |
| GCIS區域窗口 | MVP 3、6或12個完整月；預設3 | 區域公司事件觀察窗；全市背景另用12月對前12月 |
| 招募起迄月份 | 起月≤迄月，最多12月 | 純企業規劃的月目標 |
| 淨新增到職人數 | 正整數；建議上限100,000作輸入保護 | 月目標與總目標，不改官方指標 |

`manufacturing_division=29` 與 `occupation_keyword=CNC` 是兩條查詢條件。沒有統編／職缺雇主正式行業串接，就不能把結果稱為「中類29公司發布的CNC職缺」。

觀測模式不是模型預測月份。使用者招募時間在未來，不會讓系統查到未來職缺。

### 招募人數的有效用途

設總目標H、含起迄月份共M月：`base=H//M`、`remainder=H%M`。前remainder個月加1，其他月用base。

合成規劃例：2026-11至2027-01共3月，31人分11／10／10；改60人即20／20／20。

固定標示「你的淨到職目標；不代表預測可招到」。此規劃未估離職替補、招募漏斗及到職延遲。不能以H除以公開需求人數生成風險分數。

## 3. 時間對齊與歷史模式

原則是「同一資料組跨區一致；不同資料組各自標期別」。

| 資料組 | 最新模式 | 固定月份模式 |
|---|---|---|
| 職缺 | 使用來源最新發布快照；各區同日且稽核一致 | 只用該月已留存的快照，選月內最後一個；無則UNKNOWN |
| 區域GCIS事件 | 以來源已完整取得的月份作窗口終點 | 截至指定月底，要求整窗檔案與定義一致 |
| 工廠 | 跨區同一可用快照，不各自找不同年月 | 使用截止月底前的最近完整快照；顯示其真實年月與落後期 |
| 全市新設統計 | 最新可用完整月序列 | 不取目標月底之後的觀測期 |
| 薪資 | 全市同一年度、同一統計口徑 | 選觀測期不晚於指定月的目前留存版本，明示今天版本回看，不宣稱當時可得 |

必須拆開兩種歷史用途：

- **回看觀測期：** 今天取得的訂正版可以回看舊月，但要標示「以今天取得的資料回看」。
- **重現當時可知資訊：** 另需 `published_at≤knowledge_cutoff`。沒有來源發布版本／時間證據時，回 `HISTORICAL_VINTAGE_NOT_AVAILABLE`，不能宣稱無未來資訊。

MVP提供第一種。契約保留`knowledge_cutoff`但只允許null，避免把目前稅籍標籤回填歷史當成當時知道的產業。

職缺目前既有服務採最新全域快照。最新快照缺某區稽核時，MVP保留既有整組拒絕比較的行為；不自動退到舊日。使用者可另選有快照的較早月份，再取該月最後快照建立新報告。MVP不提供任意指定舊日的表單欄位；snapshot_date由resolve後端固定。

解析結果分別保存`local_observation_window`與`city_background_comparison_windows`。前者依3／6／12月輸入，後者固定近12月對前12月；固定月模式均不晚於指定月底。頁面分別標期別，不能讓使用者以為全市方向也是近3月。

## 4. 報告資訊架構

### 報告首屏

- 情境標題：地區、中類、職類、企業招募計畫。
- 來源期別列：職缺日、GCIS窗、工廠月、薪資年，不顯示含糊的單一「更新時間」。
- 回看歷史時，首屏同時標示目前資料版本取得日與GCIS分類標籤時點；不能只藏在證據抽屜。
- 三句內摘要：可比較的差異、GCIS線索、尚無法判斷的事。
- 操作：修改條件建立新報告、列印、下載JSON。

### 並排比較表

| 組別 | 指標 | 使用限制 |
|---|---|---|
| 公開職務刊登 | 刊登筆數、刊登需求人數、不同公司名稱數、主要職類 | 同日同篩選；公司名稱去重不等於法人統編去重 |
| 區域公司事件 | 已分類樣本新設、具相鄰狀態資格的資本增加、解散可用性 | MVP只描述；跨缺口資本增加另列完整觀察區間，不進窗口事件合計 |
| 工廠分布 | 能精確對應之區×中類工廠數 | 工廠不是公司總數，也不代表徵人企業 |
| 人才培育選配 | 有審核映射的相關畢業／年級管線 | 無映射時顯示尚未接入；不推算留臺中可招人數 |

全市趨勢、年度平均投保薪資及全市預測只在「共同背景」顯示一次，不複製成各區數字。平均投保薪資不改名為職缺開薪或實領薪資。

可排序的列只能使用可比較的公開樣本數值。使用者選了三區，其中一區被截斷或未知，不能給三區總排名。MVP取消整列排名；各區仍可顯示有標示的觀測值。

### 證據抽屜

每個Fact可開啟：來源名稱／網址、資料集與快照ID、觀測期、取得時間、地區與篩選、聚合欄位、去重規則、排除筆數、涵蓋與未知、ETL／映射版本、Fact／Claim ID。

不要只列一串網址。應能說清楚這句話為何由這些列與公式支持。

### 企業計畫與下一步

顯示月目標、GCIS規則觸發的查證工作，以及企業仍需確認的薪資、班別、交通與招募渠道。下一步以固定action_id和理由呈現，不產生「最佳擴廠地點」。

## 5. API設計

| API | 回傳／行為 |
|---|---|
| `GET /api/comparison-options` | 區、中類碼及版、可用職缺日、來源可用月、profile版、允許窗口 |
| `POST /api/reports/expansion-comparison/resolve` | 驗證Scenario，解析並固定release與期別，回resolution_token及預覽；不呼叫LLM |
| `POST /api/reports/expansion-comparison` | 接`{scenario, resolution_token}`，驗證已確認版本，產生Facts／Claims／摘要並保存；成功建立201 |
| `GET /api/reports/{id}` | 讀取同一不可變報告，回200；不存在404 |
| `POST /api/reports/{id}/questions` | `{question}`；依本報告Catalog產生AnswerPlan及已核驗blocks |
| `GET /api/reports/{id}/export?format=html` | 同ReportViewModel的列印版 |
| 同上`format=json` | 具版本的結構化報告；保留unknown與限制 |

職缺聚合重用`get_district_job_comparison`，報告服務直接呼叫共用函式。擴充明確的`snapshot_date`參數；不傳仍保留既有行為。不得在新orchestrator複製一套SQL後逐漸產生兩種算法。

輸入錯誤回422；既有查詢API原400保持相容。資料不足仍可建立201的LIMITED／UNAVAILABLE報告，原因列在內容。來源讀取系統錯誤、報告保存或必要稽核失敗回503；不能把所有503吞成0筆。

`POST`支援Idempotency-Key：同key同正規化輸入回原報告；同key不同輸入回409。來源已變更也不改原報告，明確「建立新版」才用新快照。

resolve保存正規化scenario hash、固定manifest、過期時間與不可猜token。建議15分鐘有效，實際值為部署設定。建立時必須比對相同scenario；過期或來源版本已無法讀取回409並要求重新確認。ETL已更新但舊release仍可讀時，仍用使用者確認的舊release，不偷換latest。

## 6. 保存與版本一致性

建議先用SQLite新增：

- `comparison_reports`：report_id、scenario、manifest_hash、版本、狀態、created_at、parent_report_id、expires_at。
- `report_payloads`：report_id、不可變JSON、payload_sha256；報告與payload同交易寫入。
- `report_answer_events`：request_id、event_id、report_id、catalog_hash、render_digest、狀態。
- `report_build_events`及Idempotency結果：與Report、payload在同一SQLite交易提交。JSONL若保留，作提交後可重試的投影，不作另一個無法原子提交的唯一真值。

API回應遺失時，同Idempotency-Key讀回原commit。不要在Report已提交後因JSONL投影失敗再建第二份報告。

MVP可將有限Facts／Evidence／Claims存在payload中，不必先做大型圖資料庫。輸出不保存完整職缺全文；只留必要的聚合與來源列鍵。圖表／頁面／匯出都使用已保存ViewModel，不重新查「最新」。

建議本機展示保留報告至決賽結束後再依設定清理；確切保存日數不是功能正確性的必要條件。過期回410並讓使用者明確建立新版。UUID不是存取授權；若上公開服務，需沿用登入權限或加入報告存取token，不能僅憑知道id就讀企業情境。

## 7. 錯誤與空狀態

| 事件 | 畫面與計算行為 |
|---|---|
| 完整稽核但0職缺 | 「本快照無符合刊登」；不說沒有缺工 |
| 查詢達上限 | 「至少N筆」；停用排名與百分比差異 |
| 缺區稽核 | 職缺組不可比較；保留GCIS等其他可用組 |
| 歷史月無職缺 | 「該月未留存快照」；不借用未來資料 |
| GCIS缺月／分類不足 | 無效指標UNKNOWN；樣本描述與證據缺口另列 |
| 無金鑰／模型超時 | 規則報告與匯出可用；AI採標準主張排列 |
| 資料更新中 | 使用已固定發布版；不能讀到一半新一半舊 |

手機版比較表放在可橫向捲動容器，保留列名稱與表頭；未知與下限用文字及符號，不只用顏色。證據開關與匯出可用鍵盤。

## 8. 完成定義

變更地區、中類、職類、觀測月及招募計畫時，只有有依據的模組變動。原報告、追問與匯出在ETL更新後仍一致。所有排名均能說明比較資格；資料不足時仍可完成一份誠實的有限報告。
