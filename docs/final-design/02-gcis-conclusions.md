# 設計二：讓GCIS真正影響產品結論

狀態：保留設計 v1；GCIS規則與捕獲已實作，區域分類來源缺口見 [交接](../REPORT_IMPLEMENTATION.md)。目的在改變可說的摘要與查證行動，不將企業登記直接轉成缺工機率。

## 1. 定義實質加值

GCIS接入後，必須至少改變其中一項：

1. 使用者看到的有證據摘要。
2. 哪一項比較可以成立、哪一項應被阻擋。
3. 企業下一步優先查證的事項及其理由。

不能只增加資料卡，卻讓摘要與行動完全相同。也不能為了顯示有影響，任意更改人才風險分數。

## 2. 兩條證據線

| 線 | 名稱與母體 | 允許用途 | MVP禁止用途 |
|---|---|---|---|
| A | `OFFICIAL_CITY_AGGREGATE`，官方全市×製造業大類×月統計 | 完整窗口的總量、方向與全市背景 | 拆成行政區、中類或職類 |
| B | `CLASSIFIED_EVENT_SAMPLE`，清冊中成功辨識區域及中類的事件樣本 | 已分類觀察數、個別來源與查證線索 | 完整區域新設／退場量、區域勝負、缺工風險 |

現有品質報告記錄新設分類率中位61%、解散0%、增資85%。這是全市同事件月份的分類比例，不能改標為某區某中類的涵蓋率。

即使分類率100%，也不證明標籤正確、當年行業正確或來源完整。80%不能作為從樣本升級母體統計的開關。保留現有低涵蓋解散屏蔽；新用途資格仍需逐項判斷。

## 3. 資料層與遷移

現有`tc_mfg_company_events_monthly`已聚合，無法單靠它重建每家公司之分類、去重及前後資本狀態。正式主張需回到既存清冊建立影子資料層。

| 邏輯表 | 必要欄位 | 功能 |
|---|---|---|
| `gcis_source_snapshot` | snapshot_id、dataset_id、source_url、source_file_id、list_month、fetched_at、published_at或null、raw_sha256、retained_sha256、parser_version、取得／解析狀態 | 記錄來源與轉換後檔案，驗每月有無完整取得 |
| `gcis_event_observation` | observation_id、snapshot_id、row_key、統編、原事件種、核准日、清冊月、事件時地址區、資本額與口徑、parse_flags | 保留可重現的觀察，不在這層猜行業 |
| `gcis_canonical_event` | event_id、統編、事件種、核准日、觀察refs、重複／衝突／有效狀態、release_id | 去重、衝突與訂正版 |
| `gcis_event_classification` | event_id、行業碼／版、來源、label_as_of、valid_from/to、回填旗標、歧義集合、審核狀態、mapping_version | 明確記錄產業標籤如何取得 |
| `gcis_window_assessment` | scope、window、purpose、classification_version、source_release、quality、原因碼、支持的Fact IDs | 判斷描述／比較／淨變化是否成立 |

`raw_sha256`是下載內容雜湊，`retained_sha256`是清理後檔案雜湊；兩者不能混成同一個檔案的hash。原始檔若因必要欄位或隱私政策不保留，記清取得證據與留存限制，不宣稱可從清理檔重現原始位元組。

聚合view依「區域×中類×核准月×事件×分類版×發布版」輸出：事件數、不同統編數、未解析地址數、未分類數、歧義與衝突數、基準資本未知數、可追溯來源。

缺月清冊在manifest以MISSING標示；沒有聚合列不代表0。

## 4. 事件與分類規則

### 去重與衝突

- 統編以八碼字串正規化，不靠公司名稱合併。
- 優先使用官方核准／登記事件識別碼。
- 沒有識別碼時，`統編＋事件種＋核准日`只作候選群組。
- 同群組語意與值相同的重刊可合併，保留全部觀察來源。
- 同日不同資本額／區域，無可靠排序證據則標CONFLICT，退出衍生比較。
- 同公司同月三次有效變更，可有三次事件；「發生變更的公司數」只算一家。
- 不將新設與增資公司數直接相加稱同業公司總數。

### 區域與時間

事件日使用核准日；清冊月份只記來源版本。不能把清冊檔名當事件發生月。

區域指公司登記所在地，不等同工廠、產線或工作地點。地址變更同時保留前後區域；不能把遷入公司的既有資本都稱為當地新增投資。

### 歷史行業標籤

當前稅籍／API標籤回填歷史，標`CURRENT_LABEL_RETROSPECTIVE`。`label_as_of`與事件日期都保留。

已解散公司較可能查不到當前稅籍，屬可能影響樣本的漏失機制，不能只刪除後認為沒有退場。營業項目第一順位到行業中類的多解映射應保留歧義，不取第一碼後默認精準。

修改映射版時，整個比較窗口以同一版重算，不把新版最新月接到舊版歷史月。

### 資本增加

資本事件需有同法律主體、同幣別、同欄位口徑且日期嚴格較早的前值。

| 情況 | 輸出 |
|---|---|
| 首次出現即變更，沒有前值 | `BASELINE_UNKNOWN`；不是0，也不是全部資本都增加 |
| 前後值可比且後值較高 | 已知狀態間資本增加；保存前後日與差額 |
| 中間來源不完整 | 只稱兩次已知狀態間增加，不宣稱該次核准精確增資，也不計入最近窗口增資合計 |
| 金額相同 | 未觀察到增加，不能推論從未擴產 |
| 缺值、同日先後不明或口徑切換 | UNKNOWN，不計入確定增加公司數 |

## 5. 按用途決定資格

資本觀察保存`baseline_date、current_state_date、comparison_span、event_precision`。只有中間變更來源完整、可確認相鄰有效狀態的`EXACT_ADJACENT_EVENT`才可計入該核准月的窗口增加事件。`BETWEEN_OBSERVED_STATES`另列完整觀察區間。例如2023年至2026-08才知道有增加，不能把差額全算在2026近3月；它觸發資料限制，不觸發窗口內增資事件規則。

`qualification`之外，必須保留`population_scope`及`purpose`。

Fact.quality保存POINT_DESCRIPTION用途的資格。其他用途由獨立assessment保存，鍵包含`purpose＋範圍＋窗口＋release＋分類版`；比較／差額／跨期Claim必須引用`assessment_refs`。不能把Fact可描述的資格直接當成比較資格。

| 用途 | 官方全市統計 | 區域分類樣本MVP |
|---|---|---|
| `POINT_DESCRIPTION` | 有明確來源、值及期別即可按scope描述 | 可描述「已分類樣本觀察到N家」，保留限制 |
| `WITHIN_SERIES_CHANGE` | 完整等長窗、同定義才可比較 | 不產生方向、增減百分比；可列各期觀察及涵蓋變化 |
| `CROSS_REGION_COMPARISON` | 全市統計不適用 | 不產生勝負或區域排序 |
| `NET_CHANGE` | MVP不開放 | 禁止，尤其解散資料不足時 |
| `HIRING_CAUSAL_INFERENCE` | 禁止 | 禁止 |

官方「新設減解散」即使計算上成立，也不自動等於企業存量變化；若未處理遷移、改組、口徑與其他事件，不能稱淨增公司存量。因此MVP整體不開NET_CHANGE。

### 零與未知

| 狀態 | 顯示文字 | 不允許的解讀 |
|---|---|---|
| 官方明列0、來源完整 | 「官方該期為0家」 | 擴張或招聘一定為0 |
| 完整收到清冊但已分類樣本無命中 | 「已分類樣本未觀察到」 | 該區沒有同業活動 |
| 清冊缺月、解析失敗、分類不可用 | 「資料不足」 | 用0補進合計／排名 |

## 6. 規則引擎：輸出Claims及下一步

規則只使用FactLedger；不讓模型自行決定觸發條件。

| ID | 必要條件 | 核准摘要／影響 |
|---|---|---|
| `GS01_CITY_NEW_UP` | 官方全市最近完整12月總量>前12月；兩窗同定義 | 說明全市新設活動增加；新增確認相關職類徵才動向的查證理由 |
| `GS02_CITY_NEW_DOWN` | 同上但下降 | 說明全市新設活動減少；不生成容易招人的結論 |
| `GS03_LOCAL_ACTIVITY` | 指定區×中類有有效已分類事件 | 列觀察樣本及分類依據；新增查證同職類招聘的工作 |
| `GS04_LOCAL_PARTIAL` | 當前標籤回填、分類或地區不完整 | 摘要優先指出限制；停用區域GCIS排名與方向箭頭 |
| `GS05_SAMPLE_ZERO` | 整個指定窗必要清冊取得且解析通過、分類已完成、樣本集合可定義且命中0 | 顯示未觀察到；不減少查證工作、不給低風險 |
| `GS06_NET_BLOCKED` | 請求淨增、退出率或擴張大於退場 | 阻擋並附缺少的用途資格與資料原因 |
| `GS07_SOURCE_UNAVAILABLE` | 缺月、衝突、來源讀取或版本不可用 | 將同業動向改為待補；列明應補哪個來源 |
| `GS08_SCOPE_DIFFERENCE` | 使用者要求把全市方向等同區域樣本 | 解釋範圍不同；不互相抵銷、不合成分數 |

`GS01/02`沒有任意「高成長」門檻。前期為0不顯示百分比；只顯示0到N的絕對變化。24個月份不完整就不產生該比較，不能用最近24列替代。

全市背景比較窗與使用者區域觀察窗分開存。兩個12月窗均以resolve所固定且不晚於觀測截止月的合格月份為終點，不改用今天最新資料。樣本集合完全無法定義或來源缺月時，不觸發GS05，改為UNKNOWN與GS07。

下列欄位由規則產出：

```json
{
  "gcis_context_claim_ids": ["由後端建立的claim_id"],
  "blocked_comparisons": [{"purpose": "NET_CHANGE", "reason_code": "GQ_DISSOLUTION_UNAVAILABLE"}],
  "next_actions": [{"action_id": "CHECK_RELATED_JOB_CHANNELS", "trigger_rule": "GS03_LOCAL_ACTIVITY", "claim_refs": ["由後端建立的claim_id"]}]
}
```

動作次序以固定規則排序：先顯示會使判斷無效的證據缺口，再列有來源的相關活動查證，最後列一般企業待確認條件。這是查證工作的順序，不是地區風險排名。

## 7. GCIS與職缺的關係

將「中類可能相關職類」作人工審核的版本化多對多表；不設虛構員工權重。GCIS的公司地址與職缺工作地點不同，兩者並列時都揭露。

沒有統編精確串接時，不能說「新增的這些公司正在招CNC」。即使精確串接成功，也只能說同一企業有可觀察刊登，不能證明新設／增資造成該職缺。

職缺只有單日快照時，不輸出「兩種趨勢同步上升」。可分別說明不同期別的觀察，再列交叉查證工作。

## 8. 有／無GCIS的驗收

採同一份合成fixture、同一職缺與企業計畫，建立對照：

- 無GCIS：同業證據待補；仍顯示同樣職缺與月目標。
- 有官方全市方向：增加全市背景與GS01/02的理由。
- 有區域樣本：增加GS03的查證活動及GS04的限制。

預期變動是GCIS Claims、證據缺口及下一步；其他來源數值完全不變。

這只能證明「資料真的影響產品行為」。要證明更有用，另做企業試用；要證明提高預測效果，需有真實結果、固定時間切分及有／無GCIS模型比較。三者不共用一個「準確率」。

## 9. MVP遷移與完成條件

固定舊版與來源hash → 從原始檔建影子事件層 → 驗去重／衝突／資本／分類 → 產用途資格 → 發布不可變release → 新增`get_gcis_business_context`唯讀服務 → 接入Report／ClaimBuilder → 正式白名單切換。

舊聚合CSV只供對照，不作唯一真值。新舊差異要能解釋，保留回退release；不在賽前覆寫唯一可運行資料。

完成時須有：官方全市方向卡、區域樣本證據卡、用途資格判定器、規則ID及原因、GCIS對照測試、每個主張的Fact／Evidence鏈。
