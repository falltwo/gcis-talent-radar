# 競賽執行路線圖

> 目標：把目前的研究型展示，收斂成一套站在企業決策者角度、資料可信、預測可驗證、AI 可治理的人才風險評估工具。

## 核心產品定位

### 一句話版本

**給正在評估擴廠的台中中小製造業老闆：輸入產業與行政區，回答未來三年當地人才是充足、吃緊還是高風險，並讓每個判斷都能追溯到政府資料。**

這句話是後續決策的共同基準：

- **誰**：正在評估擴廠、增設產線或遷廠的台中中小製造業老闆。
- **遇到什麼問題**：投資前無法判斷未來三年當地是否有足夠人才，以及同業搶人壓力是否上升。
- **我們給什麼答案**：依產業與行政區提供人才風險等級、預測區間、主要成因及可追溯資料來源。
- **不給什麼答案**：不預測單一企業一定能招到幾人，也不替企業做擴廠決策。

作品名稱、Demo 問題、簡報敘事，以及評分項目中的「創新性」與「實用性」，都必須能回到這句話。

## 執行順序總覽

| 階段 | 核心問題 | 主要交付物 | 完成標準 |
|---|---|---|---|
| 1. 產品定位 | 為誰解決什麼決策問題？ | 一句話定位、作品名稱、Demo 主問題、評審說法 | 10 秒內能說清楚，且不誇大能力 |
| 2. 整理資料 | 數字是否真實、可更新、可追溯？ | GCIS 月份清冊、台灣就業通資料、真實校務資料、資料字典 | 正式展示不含模擬資料，每個指標可追到來源 |
| 3. 預測引擎 | 未來三年的風險如何估計？ | 統計基線、回測結果、Chronos 比較、預測區間 | 有樣本外誤差，且不只輸出單一數字 |
| 4. AI 解說 | AI 如何安全地解釋結果？ | OpenRouter 串接、模型白名單、指標白名單、數字驗證器 | AI 不自行計算或捏造數字 |
| 5. 治理機制 | 不當問題與高風險輸出如何攔截？ | KeywordScopeGuard 閘門、Prompt Guard、拒答政策、稽核日誌 | 招募歧視問題能攔截，事件可追查 |
| 6. 評測 | 系統效果能否量化證明？ | 回測誤差、幻覺率、攔截率、測試報告 | 所有競賽主張都有實測數字支撐 |
| 7. 企業介面 | 老闆能否快速完成一次決策評估？ | 企業版流程、風險結果頁、證據頁、三分鐘 Demo | 不懂模型的使用者也能完成任務 |

## 1. 產品定位

### 要做的事

1. 定稿一句話定位，所有成員使用同一版本。
2. 決定作品名稱，名稱應讓人聯想到「擴廠、人才、風險」，避免只像學術研究平台。
3. 定義一個 Demo 主問題，例如：
   - 「我想在大雅區擴建精密機械產線，未來三年的人才風險有多高？」
4. 用相同定位改寫評審說法：
   - **創新性**：把 GCIS 企業動態轉成區域搶人訊號，再與職缺和人才供給結合。
   - **實用性**：在設備、土地與訂單之外，讓中小企業能在投資前先量化人才風險。
5. 明確寫出產品邊界，避免將「風險評估」說成「保證招得到人」。

### 交付物

- 一句話定位。
- 作品名稱候選與選定理由。
- Demo 主問題與標準答案結構。
- 30 秒、1 分鐘及 3 分鐘三種版本的產品介紹。

### 驗收標準

- 第一次聽到的人能回答「使用者是誰、問題是什麼、系統給什麼答案」。
- Demo、介面、資料和模型都服務同一個決策情境。
- 沒有「保證招到人」或「精準預測單一企業人數」等過度承諾。

## 2. 整理資料

### 2.1 GCIS 企業動態

- 接入 GCIS 月份清冊：**新設、解散、變更**。
- 統一公司、行業、行政區和月份欄位。
- 將公司變更拆成可解釋事件；若要把增資視為擴張訊號，必須保留原始欄位和判定規則。
- 建立每月更新流程、去重規則與資料品質檢查。

### 2.2 職缺資料

- 將現有 104 職缺資料改為**台灣就業通等政府公開資料**。
- 記錄職缺的產業、職類、地區、刊登時間及需求人數；缺少的欄位不可自行推測。
- 建立職類與目標產業的固定對照表，版本化管理映射規則。

### 2.3 校務與人才供給資料

- 移除正式展示流程中的模擬校務資料。
- 只使用可說明年度、學校、系所、欄位定義與來源網址的真實資料。
- 若真實資料尚未取得，介面應顯示「資料不足」，不可用模擬值補成正式結論。

### 交付物

- 原始資料清單與資料字典。
- 可重跑的 ETL 管線。
- 產業、職類、科系及行政區映射表。
- 資料來源、更新日期、授權條件與處理步驟。
- ETL 品質報告。

### 驗收標準

- 正式 Demo 使用的每個數字都能追到原始資料與轉換規則。
- 展示資料中不含未標示的模擬資料。
- 同一份輸入能穩定產出相同結果。

## 3. 建立預測引擎

### 3.1 先定義預測目標

預測對象應是可由資料支持的區域產業訊號，例如：

- 特定行政區與產業的企業新設、解散或變更趨勢。
- 特定地區與職類的職缺需求趨勢。
- 相關科系人才供給趨勢。
- 綜合以上訊號形成的人才風險等級。

不直接預測「某家公司三年後一定能招到幾人」。

### 3.2 統計模型基線

- 先建立簡單且可解釋的基線，例如季節性 naive、移動平均、指數平滑或 ARIMA 類模型。
- 使用時間序列切分或 rolling backtest，禁止把未來資料洩漏到訓練期。
- 至少計算 MAE、RMSE；若資料含零值，謹慎使用 MAPE，必要時改用 WAPE 或 sMAPE。

### 3.3 時序模型

- 再加入 Chronos 類預訓練時序模型。
- 使用完全相同的回測區間與指標，和統計基線公平比較。
- 若 Chronos 沒有優於基線，應誠實保留基線，不為了使用 AI 而使用 AI。

### 3.4 輸出方式

- 輸出中位預測與預測區間，例如 P10／P50／P90 或 80%／95% 區間。
- 顯示模型版本、訓練資料期間、預測期間與最近一次更新時間。
- 將模型結果轉成「低／中／高風險」時，保留明確且版本化的門檻規則。

### 交付物

- 基線模型與 Chronos 模型。
- 回測腳本與結果表。
- 預測區間與區間覆蓋率。
- 模型卡：用途、限制、資料期間、已知風險。

### 驗收標準

- 每個模型都有樣本外測試結果。
- 能回答「比簡單基線好多少」。
- 使用者看到的是區間與風險，不是偽精準的單一數字。

---

## 4. 串接 AI

### 要做的事

1. 透過 OpenRouter 串接通過團隊審核的**非中資模型**。
2. 建立模型白名單，固定可用模型與版本，避免執行時任意切換。
3. 建立核准指標白名單，LLM 只能引用後端提供的欄位。
4. 數值計算由確定性程式完成；LLM 只負責解釋與組織文字。
5. 數字驗證器逐一比對 AI 回答中的數值、單位、期間、地區及來源。
6. 找不到核准資料時，AI 必須回答「資料不足」，不可補值或猜測。
7. 回答中附上資料來源、更新時間及模型／規則版本。

### 交付物

- OpenRouter 串接模組與模型白名單。
- 指標白名單及工具 schema。
- 數字驗證器。
- 有引用、拒答與資料不足處理的回答格式。

### 驗收標準

- LLM 無法直接讀取未核准資料表或自由產生指標。
- 回答中的數字全部通過驗證器，否則不得呈現給使用者。
- 關閉 LLM 後，核心風險分數與預測結果仍可正常產生。

---

## 5. 建立治理機制

### 要做的事

- 使用 KeywordScopeGuard 閘門判斷請求是否在產品允許範圍內。
- 加入 Prompt Guard，攔截提示注入、越權資料要求與政策規避。
- 對涉及招募歧視的問題拒答，例如性別、年齡、婚育、身心狀況等不當篩選。
- 拒答時以清楚理由和合法替代問法引導使用者。
- 保留稽核日誌：時間、請求類型、命中規則、處理結果、模型版本、驗證結果。
- 日誌避免記錄不必要的個資或完整敏感內容。

### 交付物

- KeywordScopeGuard 決策規則。
- Prompt Guard 規則與攻擊測試集。
- 招募歧視拒答政策與測試題。
- 結構化稽核日誌及查詢頁面。

### 驗收標準

- 正常企業問題能通過，不當招募問題能穩定攔截。
- 每次攔截或放行都有可追查的原因。
- 稽核日誌不暴露不必要的敏感資料。

## 6. 執行評測

### 核心指標

| 面向 | 建議指標 | 說明 |
|---|---|---|
| 預測 | MAE、RMSE、WAPE／sMAPE | 與統計基線在相同回測區間比較 |
| 預測區間 | Coverage、平均區間寬度 | 檢查真值落在預測區間內的比例 |
| 數字可信度 | 數字一致率、來源覆蓋率 | 回答中的數字是否和核准資料一致且附來源 |
| 幻覺 | 幻覺率 | 無來源、錯數字、錯期間或錯地區都計入 |
| 治理 | 攔截率、誤攔率、漏攔率 | 同時測惡意問題與正常問題 |
| 系統 | 成功率、回應時間 | 確認 Demo 現場的穩定性 |

### 評測方法

- 建立版本化的 Golden Questions，涵蓋正常查詢、資料不足、數字核對、越權要求與歧視問題。
- 固定資料版本、模型版本、提示版本與測試日期。
- 所有競賽簡報上的百分比都必須能由評測輸出重現。
- 保留失敗案例，說明問題、修正方式及修正後結果。

### 交付物

- 回測報告。
- AI 幻覺與數字核驗報告。
- 治理攔截測試報告。
- 可供簡報使用的指標摘要與圖表。

### 驗收標準

- 回測誤差、幻覺率和攔截率皆為實際執行結果。
- 指標定義、分母和測試題數清楚揭露。
- 評審可依 repository 內容重現結果。

## 7. 改造企業版介面

### 建議使用流程

1. **描述擴廠情境**：選擇產業、行政區、預計時間及新增職類。
2. **先看結論**：顯示未來三年人才風險等級與預測區間。
3. **理解原因**：拆解同業新設／解散／變更、職缺競爭與人才供給。
4. **查看證據**：點開每個指標的來源、期間、更新日期與計算方式。
5. **比較情境**：比較不同行政區或產業情境，不替企業做最終決策。
6. **詢問 AI**：只能針對目前核准資料做解釋與追問。

### 首頁應直接回答

- 這是給誰用的？
- 輸入什麼？
- 會得到什麼答案？
- 為什麼可以相信？
- 哪些事情系統不會替你決定？

### Demo 黃金路徑

以一個具體情境完成三分鐘展示：

> 「一家精密機械中小企業準備在大雅區擴產，系統如何判斷未來三年的人才風險？」

展示順序：輸入情境 → 看風險結論與區間 → 展開三項主要原因 → 點開資料來源 → 詢問 AI → 示範歧視問題拒答 → 顯示評測數字。

### 交付物

- 企業版資訊架構與主流程。
- 情境輸入頁、風險結果頁、證據抽屜、比較頁與稽核頁。
- 三分鐘 Demo 腳本與備援畫面。

### 驗收標準

- 第一次使用者不需要理解 Z-score、模型名稱或資料表即可完成評估。
- 第一屏先呈現企業問題與決策答案，不先呈現技術架構。
- 三分鐘內能走完一個完整情境，且每個結論都能打開查證。

## 相依關係與工作原則

```text
產品定位
   ↓
資料可信度
   ↓
預測基線與回測
   ↓
AI 解說 ── 治理閘門
   └──────┬──────┘
          ↓
        實測評估
          ↓
      企業版介面與 Demo
```

工作原則：

1. **先有真實資料，再談模型效果。**
2. **先有簡單基線，再加入 Chronos。**
3. **數字由程式產生，LLM 只做解釋。**
4. **沒有來源的數字不上畫面。**
5. **沒有實測的百分比不上簡報。**
6. **介面先回答企業問題，再展示技術。**
